# Relational Row Claims
 
How workers safely claim rows from a shared table: the claim columns, the optional columns that sit next to them, indexing, and the locking queries for each database.
 
**Out of scope:** what the work does, shutdown behavior, failure history, metrics and alerting. Those are application or observability decisions; don't add them here.
 
## Before implementing: confirm these decisions with the user
 
Ask before writing any schema or code. Don't pick answers silently, even when a default is noted.
 
1. **Existing table or new table?** Default preference: add the columns to the existing table being processed, so there's nothing extra to join. Ask anyway.
2. **`claim_id` source:** passed in, generated by the database, or both (passed in if given, generated otherwise)?
3. **`claim_type`:** can a row be claimed for more than one kind of work?
4. **Claim duration** (default).
5. **Which add-ons does this claim need?** Ask about each one; any combination is valid, including none (see "Add-on columns"):
   - **Status:** if yes, confirm the values `pending`, `completed`, `retry`, `failed`.
   - **Attempt count:** count attempts?
   - **Attempt limit:** stop claiming after `max_attempts`, or retry forever? If limited, confirm the default.
   - **Retry timing:** wait before a row can be claimed again?
   - **Failure message:** record why the last attempt failed?
   - **Deadline:** stop claiming after a time window (e.g. one week)? If yes, confirm the window.
## Claim columns (always)
 
Use these names. Don't invent alternatives (`locked_by`, `lease_until`, `owner`, etc.).
 
| Column | Type (Postgres) | Meaning |
|---|---|---|
| `claim_id` | `uuid NULL` | A new token on every claim (passed in or generated). It's a fencing token: it proves the current worker still holds the claim. |
| `claimed_by` | `text NULL` | Identity of the worker (host, pod, process id). For debugging only, never for correctness. |
| `claim_expires_at` | `timestamp NULL` (UTC) | When the claim lapses. **The source of truth for whether a row is claimed.** |
| `claim_type` | `text NULL` | Only if a row can be claimed for more than one kind of work. Set at claim time. |
 
A row is claimed when `claim_expires_at` is in the future, and free when it's `NULL` or in the past. Never decide this from `claim_id` or `claimed_by`; they can hold stale values from an expired claim, and that's fine.
 
A row is being processed when its claim is active. There is no `processing` status.
 
### Claim ID source
 
- **Passed in:** when the app needs the ID before the claim (tracing, logging, reading claimed rows back by `claim_id`). It must be new and unique for every claim call.
- **Generated:** when the caller doesn't need it up front. The claim query returns it.
Support both with `COALESCE(:claim_id, <db uuid function>)`. A batch claim puts the same `claim_id` on every row in the batch; that's fine because later writes are fenced on `id AND claim_id`.
 
## Add-on columns (each optional, ask)
 
Each add-on can be used on its own or with others. The queries below tag every add-on line with the add-on's name in a comment (e.g. `-- [status]`); leave out the lines for add-ons that aren't used.
 
| Add-on | Columns (Postgres) | What it does | Typical use |
|---|---|---|---|
| **[status]** | `status text NOT NULL DEFAULT 'pending'` | Tracks the row's outcome: `pending`, `completed`, `retry`, `failed`. Only `pending` and `retry` are claimable. Plain text, **not** an enum and **no** CHECK constraint, so values can change without a migration. | Rows that finish (one-off work). Not needed when rows are processed again on every pass. |
| **[attempts]** | `attempts int NOT NULL DEFAULT 0` | Counts attempts. Incremented **at claim time**, so a worker that crashes mid-attempt still counts. | Any time the count matters, with or without a limit. |
| **[max attempts]** | `max_attempts int NOT NULL DEFAULT <confirmed>` | Stops claiming once `attempts` reaches it. Requires [attempts]. Leave it out to retry forever. | Work that should give up after N tries. |
| **[timing]** | `last_attempt_at timestamp NULL`, `next_attempt_at timestamp NOT NULL DEFAULT (now() AT TIME ZONE 'UTC')` (UTC) | `last_attempt_at` is set at claim time. `next_attempt_at` is the earliest time the row may be claimed again; it holds the retry delay with jitter. | Backoff between retries, or not hammering a failing dependency. |
| **[failure message]** | `failure_message text NULL` | Why the latest attempt failed. Overwritten on each failure. | Seeing at a glance why a row is retrying or failed. |
| **[deadline]** | `deadline_at timestamp NULL` (UTC) | Stops claiming after this time, even if attempts remain. Set when the row is created (e.g. created time + 1 week). | Work that can become pointless, e.g. polling an API for a result that may never arrive. |
 
How they combine:
 
- **Unlimited retries:** use [attempts] without [max attempts], or neither.
- **Limited retries:** [attempts] plus [max attempts].
- **Ending as `failed`:** a row only becomes `failed` with [status] plus [max attempts] or [deadline]. Without those, failures go back to `retry` (or just release the claim, without [status]).
- **[deadline] or [max attempts] without [status]:** the row simply stops being claimed once it hits the limit.
## Indexing
 
Always index what the claim query filters and sorts on, so workers don't scan the whole table on every poll. Use a partial index where the database supports it, so it only covers rows that can still be claimed.
 
```sql
-- Claim columns only
CREATE INDEX jobs_claim_idx ON jobs (claim_expires_at);
 
-- With [timing] (sorts on next_attempt_at)
CREATE INDEX jobs_claim_idx ON jobs (next_attempt_at);
 
-- With [status] and [timing]
CREATE INDEX jobs_claim_idx
  ON jobs (next_attempt_at)
  WHERE status IN ('pending', 'retry');
```
 
Match the index to the claim query's actual `WHERE` and `ORDER BY`. If the query also filters on `claim_type` or another column, include it.
 
## Rules (every database)
 
1. **Claim in its own short transaction and commit right away.** Never hold the row lock while doing the work. After commit, the claim columns are the lock.
2. **The claim is decided only by `claim_expires_at`.** Setting it in the future claims the row; setting it to `NULL` or letting it pass releases it.
3. **Fence every later write on `claim_id`:** `WHERE id = :id AND claim_id = :claim_id`.
4. **Zero rows updated means the claim was lost.** Stop, don't retry the write. Another worker owns the row.
5. **Everything is UTC, from the database clock.** Set and compare timestamps only with the database's UTC function. The app may pass a *delay* (claim duration, retry delay with jitter) as an interval; the database adds it to its own UTC time.
6. **Expiry is the crash recovery.** If a worker is killed, its rows stay claimed until `claim_expires_at` passes, then become claimable again. Nothing else is needed.
7. **Heartbeat long work.** If work can outlast the claim duration, extend `claim_expires_at` (fenced on `claim_id`) at roughly one third of the duration.
8. **Clear all claim columns whenever a claim ends**, in the same statement as any add-on changes.
9. **Order the claim query:** by `next_attempt_at` with [timing], otherwise by a created or priority column, so work is roughly fair and the index is used.
10. **Work must be idempotent.** A claim can expire mid-work and the row can be processed twice. Fencing stops a stale worker's writes, not its side effects.
## Jitter (worker side)
 
Jitter is the workers' job, not the database's. The app computes delays with jitter and passes them in as intervals:
 
- **Retry delay** ([timing]): exponential backoff with a cap, randomized, e.g. `random_between(0.5, 1.0) * min(cap, base * 2^(attempts - 1))`. The stored `next_attempt_at` then includes the jitter.
- **Polling:** when a claim returns no rows, sleep a random time in a range before trying again, so workers don't all claim at once.
## Postgres (reference implementation)
 
Always write the current time as `(now() AT TIME ZONE 'UTC')`; never bare `now()`, `CURRENT_TIMESTAMP` or `LOCALTIMESTAMP` against these `timestamp` columns.
 
### Claim
 
```sql
WITH candidate AS (
  SELECT id
  FROM jobs
  WHERE (claim_expires_at IS NULL OR claim_expires_at < (now() AT TIME ZONE 'UTC'))
    AND status IN ('pending', 'retry')                                       -- [status]
    AND attempts < max_attempts                                              -- [max attempts]
    AND next_attempt_at <= (now() AT TIME ZONE 'UTC')                        -- [timing]
    AND (deadline_at IS NULL OR deadline_at > (now() AT TIME ZONE 'UTC'))    -- [deadline]
  ORDER BY next_attempt_at                                -- [timing]; otherwise a created/priority column
  LIMIT $1                                                -- batch size
  FOR UPDATE SKIP LOCKED
)
UPDATE jobs j
SET claim_id         = COALESCE($5::uuid, gen_random_uuid()),  -- passed in, or generated
    claimed_by       = $2,
    claim_expires_at = (now() AT TIME ZONE 'UTC') + $3::interval,
    claim_type       = $4,                                     -- only if claim_type is used
    attempts         = j.attempts + 1,                         -- [attempts]
    last_attempt_at  = (now() AT TIME ZONE 'UTC')              -- [timing]
FROM candidate
WHERE j.id = candidate.id
RETURNING j.*;
```
 
If the candidate query joins other tables, use `FOR UPDATE OF jobs SKIP LOCKED` so only the claimed table is locked.
 
### Heartbeat
 
```sql
UPDATE jobs
SET claim_expires_at = (now() AT TIME ZONE 'UTC') + $3::interval
WHERE id = $1 AND claim_id = $2;
```
 
### Release (without [status]: done or failed, either way)
 
```sql
UPDATE jobs
SET claim_id = NULL, claimed_by = NULL, claim_expires_at = NULL, claim_type = NULL
WHERE id = $1 AND claim_id = $2;
```
 
### Complete ([status])
 
```sql
UPDATE jobs
SET status = 'completed',
    claim_id = NULL, claimed_by = NULL, claim_expires_at = NULL, claim_type = NULL
WHERE id = $1 AND claim_id = $2;
```
 
### Fail (any add-on that records a failure)
 
`$3` is the retry delay with jitter from the app; `$4` is the failure message. Keep only the `WHEN` conditions for the add-ons in use. With neither [max attempts] nor [deadline], set `status = 'retry'` directly.
 
```sql
UPDATE jobs
SET status = CASE                                                            -- [status]
      WHEN attempts >= max_attempts                                          -- [max attempts]
        OR (deadline_at IS NOT NULL                                          -- [deadline]
            AND (now() AT TIME ZONE 'UTC') + $3::interval >= deadline_at)    -- [deadline]
      THEN 'failed'
      ELSE 'retry'
    END,
    next_attempt_at = (now() AT TIME ZONE 'UTC') + $3::interval,             -- [timing]
    failure_message = $4,                                                    -- [failure message]
    claim_id = NULL, claimed_by = NULL, claim_expires_at = NULL, claim_type = NULL
WHERE id = $1 AND claim_id = $2;
```
 
## Other databases
 
The columns, add-ons and rules are the same. Swap in that database's UTC function, UUID function and interval syntax to translate the Postgres heartbeat, release, complete and fail statements. Add-on lines carry the same tags.
 
### MySQL 8.0+ / MariaDB 10.6+
 
`SKIP LOCKED` is supported, but `UPDATE ... RETURNING` isn't reliably available, so use a transaction. The app needs the `claim_id` to read the claimed rows back: use the passed-in one, or generate it in the app.
 
```sql
START TRANSACTION;
SELECT id FROM jobs
WHERE (claim_expires_at IS NULL OR claim_expires_at < UTC_TIMESTAMP(6))
  AND status IN ('pending', 'retry')                                  -- [status]
  AND attempts < max_attempts                                         -- [max attempts]
  AND next_attempt_at <= UTC_TIMESTAMP(6)                             -- [timing]
  AND (deadline_at IS NULL OR deadline_at > UTC_TIMESTAMP(6))         -- [deadline]
ORDER BY next_attempt_at                                              -- [timing]; otherwise created/priority
LIMIT ?
FOR UPDATE SKIP LOCKED;
 
UPDATE jobs
SET claim_id = ?, claimed_by = ?,
    claim_expires_at = UTC_TIMESTAMP(6) + INTERVAL ? SECOND,
    attempts = attempts + 1,                                          -- [attempts]
    last_attempt_at = UTC_TIMESTAMP(6)                                -- [timing]
WHERE id IN (...ids from above...);
COMMIT;
 
SELECT * FROM jobs WHERE claim_id = ?;
```
 
- Always `UTC_TIMESTAMP(6)`, never `NOW()` or `CURRENT_TIMESTAMP` (they follow the session time zone).
- `claim_id` as `BINARY(16)` or `CHAR(36)`, timestamps as `DATETIME(6)` holding UTC, `status` as `VARCHAR`.
- MySQL evaluates `SET` assignments left to right using already-changed values. In the fail statement, put `status` (which reads `attempts` and `deadline_at`) before anything that changes them.
### SQL Server
 
Use `UPDLOCK, READPAST, ROWLOCK` (the `SKIP LOCKED` equivalent) and `OUTPUT`:
 
```sql
WITH candidate AS (
  SELECT TOP (@batch) *
  FROM jobs WITH (UPDLOCK, READPAST, ROWLOCK)
  WHERE (claim_expires_at IS NULL OR claim_expires_at < SYSUTCDATETIME())
    AND status IN ('pending', 'retry')                                -- [status]
    AND attempts < max_attempts                                       -- [max attempts]
    AND next_attempt_at <= SYSUTCDATETIME()                           -- [timing]
    AND (deadline_at IS NULL OR deadline_at > SYSUTCDATETIME())       -- [deadline]
  ORDER BY next_attempt_at                                            -- [timing]; otherwise created/priority
)
UPDATE candidate
SET claim_id = COALESCE(@claim_id, NEWID()),
    claimed_by = @worker,
    claim_expires_at = DATEADD(second, @seconds, SYSUTCDATETIME()),
    attempts = attempts + 1,                                          -- [attempts]
    last_attempt_at = SYSUTCDATETIME()                                -- [timing]
OUTPUT inserted.*;
```
 
`uniqueidentifier`, `datetime2` (UTC), `nvarchar` for `status`. Always `SYSUTCDATETIME()`, never `GETDATE()` or `SYSDATETIME()`.
 
### Oracle
 
`FOR UPDATE SKIP LOCKED` is supported, but combining it with row limiting (`FETCH FIRST` / `ROWNUM`) is restricted. Open a cursor with `FOR UPDATE SKIP LOCKED`, fetch up to the batch size in the app, update each row by `ROWID`, then commit. Use the passed-in `claim_id`, or generate one with `SYS_GUID()` once before the loop.
 
```sql
-- candidate cursor
SELECT ROWID AS rid FROM jobs
WHERE (claim_expires_at IS NULL OR claim_expires_at < SYS_EXTRACT_UTC(SYSTIMESTAMP))
  AND status IN ('pending', 'retry')                                           -- [status]
  AND attempts < max_attempts                                                  -- [max attempts]
  AND next_attempt_at <= SYS_EXTRACT_UTC(SYSTIMESTAMP)                         -- [timing]
  AND (deadline_at IS NULL OR deadline_at > SYS_EXTRACT_UTC(SYSTIMESTAMP))     -- [deadline]
ORDER BY next_attempt_at                                                       -- [timing]; otherwise created/priority
FOR UPDATE SKIP LOCKED;
 
-- for each fetched row, up to the batch size
UPDATE jobs
SET claim_id = :claim_id,
    claimed_by = :worker,
    claim_expires_at = SYS_EXTRACT_UTC(SYSTIMESTAMP) + NUMTODSINTERVAL(:seconds, 'SECOND'),
    attempts = attempts + 1,                                                   -- [attempts]
    last_attempt_at = SYS_EXTRACT_UTC(SYSTIMESTAMP)                            -- [timing]
WHERE ROWID = :rid;
```
 
`TIMESTAMP` holding UTC, `VARCHAR2` for `status`. Always `SYS_EXTRACT_UTC(SYSTIMESTAMP)`, never `SYSDATE` or `CURRENT_TIMESTAMP`.
 
### SQLite
 
No row locks and one writer at a time, so `SKIP LOCKED` isn't needed. Use `BEGIN IMMEDIATE` and `UPDATE ... RETURNING` (3.35+). `datetime('now')` is UTC; never add `'localtime'`. Write every timestamp with `datetime()` so they share one text format and compare correctly.
 
```sql
BEGIN IMMEDIATE;
UPDATE jobs
SET claim_id = :claim_id,          -- passed in, or generated in the app (no UUID function)
    claimed_by = :worker,
    claim_expires_at = datetime('now', '+' || :claim_seconds || ' seconds'),
    attempts = attempts + 1,                                        -- [attempts]
    last_attempt_at = datetime('now')                               -- [timing]
WHERE id IN (
  SELECT id FROM jobs
  WHERE (claim_expires_at IS NULL OR claim_expires_at < datetime('now'))
    AND status IN ('pending', 'retry')                              -- [status]
    AND attempts < max_attempts                                     -- [max attempts]
    AND next_attempt_at <= datetime('now')                          -- [timing]
    AND (deadline_at IS NULL OR deadline_at > datetime('now'))      -- [deadline]
  ORDER BY next_attempt_at                                          -- [timing]; otherwise created/priority
  LIMIT :batch
)
RETURNING *;
COMMIT;
```
 
### Fallback: no SKIP LOCKED
 
Optimistic compare-and-set per row; check the affected row count:
 
```sql
UPDATE jobs
SET claim_id = COALESCE(:claim_id, <db uuid function>),
    claimed_by = :worker,
    claim_expires_at = <db_utc_now> + <claim duration>,
    attempts = attempts + 1,                                        -- [attempts]
    last_attempt_at = <db_utc_now>                                  -- [timing]
WHERE id = :id
  AND (claim_expires_at IS NULL OR claim_expires_at < <db_utc_now>)
  AND status IN ('pending', 'retry')                                -- [status]
  AND attempts < max_attempts                                       -- [max attempts]
  AND next_attempt_at <= <db_utc_now>                               -- [timing]
  AND (deadline_at IS NULL OR deadline_at > <db_utc_now>);          -- [deadline]
-- <db_utc_now> = the database's UTC function: (now() AT TIME ZONE 'UTC'), UTC_TIMESTAMP(6),
-- SYSUTCDATETIME(), SYS_EXTRACT_UTC(SYSTIMESTAMP), datetime('now'). Never CURRENT_TIMESTAMP.
-- 1 row = claimed, 0 rows = someone else got it; try the next candidate
```
 
Expect more contention than `SKIP LOCKED`. Pick candidates randomly or by offset to spread workers out.
 
## Checklist
 
- [ ] User confirmed: existing vs new table, `claim_id` source, `claim_type`, claim duration, and each add-on (with status values, max attempts default, and deadline window where used)
- [ ] Standard column names; `status` (if used) is text, no enum or CHECK
- [ ] Only the chosen add-ons' lines are in the queries; [max attempts] is only used with [attempts]
- [ ] Index matches the claim query's `WHERE` and `ORDER BY`
- [ ] Claim transaction commits before work starts
- [ ] Every later write is fenced on `claim_id` and checks the row count
- [ ] All times from the database's UTC function; the app passes only delays
- [ ] Heartbeat if work can exceed the claim duration
- [ ] Every statement that ends a claim clears all claim columns
- [ ] Retry delays ([timing]) and polling have jitter
- [ ] Processing is idempotent
