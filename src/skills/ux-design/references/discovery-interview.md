# Discovery interview

Read this when beginning a new design brief, continuing a partially answered interview, or revisiting a materially changed problem.

## Prepare the next question

Extract answers from the conversation, supplied pages, screenshots, examples, and existing design system. Keep a compact record of what is known and what is uncertain. An existing screen shows current decisions; it does not prove those decisions satisfy user needs.

Choose the question whose answer would most change the design. Explain a tradeoff briefly if Brian needs context. Ask a small, coherent round rather than sending a questionnaire covering every topic below.

Start with the user's problem. Ask about visual taste after the task and content are understandable, unless the request specifically concerns visual direction alone.

## Follow the answer rather than a script

Use these branches selectively:

| When this is unclear | Ask something concrete | Follow up when it changes the design |
| --- | --- | --- |
| Purpose | What should someone accomplish here? | What happens immediately before and after? |
| Audience | Who uses it, and what do they already understand? | First visit or repeated expert work? Different roles? |
| Task priority | Which decision or action matters most? | What else must remain easy to find? |
| Current friction | Walk me through a recent difficult example. | Was the problem finding, understanding, deciding, or acting? |
| Content | Show me one realistic record, message, or offering. | What is unusually long, missing, variable, or difficult? |
| Stakes | What happens if someone makes a mistake? | What should prevent it or support recovery? |
| Device/context | Where and how will someone use this? | Interrupted work, touch, keyboard, small screens, poor connectivity? |
| Constraints | What existing brand, UI, or content decisions must be kept? | Which are requirements and which are open? |
| Personality | How should this feel to the intended user? | What visible choices would communicate that? |
| References | What specifically appeals to you in this example? | Typography, density, composition, imagery, tone, or behavior? |
| Scope | Which page or journey are we designing now? | Which adjacent screens only need to explain the flow? |
| Success | What would make you say this design works? | What observable task can we use to judge that? |

Ask for an example when an answer is abstract. "Modern" might mean calm typography, denser information, expressive imagery, or fewer steps; do not choose among those meanings silently.

Reflect a contradiction before resolving it: "You want every invoice visible at once and generous spacing. Which task needs that density, and where can detail move into an expanded view?"

When Brian says "I don't know," offer understandable choices with consequences or propose a bounded exploration. Treat the preference as unresolved until he selects an option or delegates the choice. Do not turn silence into agreement.

## Separate evidence and assumptions

Use these categories when helpful:

- **Known:** supplied facts and demonstrated behavior.
- **Preference:** Brian's chosen direction or constraint.
- **Assumption:** a provisional choice Brian has authorized you to make.
- **Question to test:** a hypothesis needing a mockup walkthrough or actual user evidence.

Avoid invented personas or research claims. "We assume mobile users review invoices more often than creating them" is testable; "mobile users only review" is an unjustified restriction.

## Decide when the interview is sufficient

Continue if competing answers would produce materially different tasks, groups, actions, states, or visual directions. Examples: unknown audience, unclear primary action, contradictory save behavior, unexplained data, or an unresolved reference preference.

Move to brief confirmation when those decisions are clear enough to design and remaining choices are delegated or explicitly scheduled for exploration. The exact font, every shade, and all possible edge cases do not need to be settled in conversation.

For a detailed supplied brief, summarize your understanding and ask only consequential gaps. For a narrow redesign, interview the affected task rather than restarting discovery for the entire product.

## Brief structure

Write a compact brief Brian can correct:

1. **Audience and situation:** who needs this and when.
2. **Outcome:** the primary job and what success looks like.
3. **Scope and flow:** entry, key decisions/actions, result, and necessary adjacent screens.
4. **Content and states:** realistic content, meaningful exceptions, and recovery needs.
5. **Direction and constraints:** character, reference qualities, existing conventions, device needs.
6. **Artifact and evaluation:** tool or isolated HTML, simulated interactions, observable acceptance criteria.
7. **Open questions:** resolved now, delegated, or deliberately explored in the design.

Keep the brief proportional to the task. Preserve it with the artifact when work spans iterations, using the existing project convention or a small design-local note. Updating the brief should not require modifying repository agent instructions.
